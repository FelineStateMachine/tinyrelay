Self-hosted Nostr infrastructure

Many relays.
One process.
Your machine.

Bring bindws’s full capabilities and user workflows to a native, self-hosted Go service. Preserve the experience of creating and running templated relays while replacing the Worker runtime with local services.

Full functional & UX parityNo fuel or leasesNo product quotasAutomatic inbox / outboxObservability from day one

Recommendation: a modular monolith with an embedded control plane, a SQLite database per named relay, and shared workers. A personal template provisions a family of relays. Public and management pages are plain HTML and basic forms, rebuilt without bindws branding or styling.

Measured Git results | 7 September 2026. Six repositories from the local Developer folder passed push, clone, fetch, and concurrent clone tests on Slate. Streaming reduced peak Go RSS from 6,094 MiB to 40.6 MiB; Atlas cloned in 9.15 seconds against an 8.92-second native Git baseline. Open the report, failures, methodology and raw data.
Completion contract: work until parity. The finished Go project must cover every existing bindws feature, protocol behavior, management action and user journey, except the explicitly agreed changes below. Intermediate phases are implementation checkpoints; a working core relay is not completion. Features that owners can switch off still have to be implemented and tested.
01 / Product
Preserve the workflows.

All relay, community, hosting and management capabilities carry forward. Templates remain the API; visual simplicity does not reduce functionality.

02 / Runtime
Local by default.

One daemon, local disk, long-lived sockets and restart-safe jobs. Capacity is determined by the machine and its workload.

03 / Engineering
Measure before tuning.

Instrument acceptance, query, fan-out and delivery before optimization. Use traces and profiles to explain benchmark results.

“No resource limits” is a product commitment. There is no maximum relay count, monthly event allowance, fuel balance or tenant storage tier in the domain model. The host still has finite RAM, disk and file descriptors. Flow control uses finite buffers, fair scheduling and connection deadlines; overload returns a clear retryable failure before acceptance. Retention, bans and authorized access remain owner-selected relay behavior.
Product UI layout. The rebuilt public and management pages use bare HTML, tables and basic forms. The fixed layout target is 960px on desktop and 360px on mobile, with no inherited bindws branding or visual system. When useful, a locally vendored Fixi project bundle (fixi, moxi, paxi, ssexi and rexi) may provide progressive form swaps, inline actions, morphing, streamed job progress and ergonomic requests. It remains an enhancement layer: signed NIP-98 mutations, accessible forms and server responses remain usable without it.
Explicit changes to the parity baseline
  • Remove fuel and product capacity entitlements: no balance, top-up, billing ledger, paid tier or inherited fixed tenant quota. NIP-57 zap event support and non-fuel notifications remain in scope.
  • Remove relay leases and trials: assign ownership at creation, including fork destinations. Preserve membership invitation codes and their claim/join workflows; those are unrelated to leasing a relay.
  • Replace cloud infrastructure: Workers, Durable Objects, R2/KV bindings, alarms and provider domain provisioning become local Go services. Preserve their user-facing capabilities through local implementations.
  • Rebuild presentation: plain HTML and forms, no bindws style or branding. Keep task flows, permissions, signers, feedback, sharing and accessible alternatives. The command is tiny.
  • Improve inbox/outbox and observability: add targeted inbox admission, persistent automation and measurement-driven performance work. Document behavioral improvements explicitly; do not silently reinterpret imported policies.

These changes do not authorize dropping unrelated features. Keep a precise source-to-target mapping for every exception and verify that its replacement workflow is complete.

Publish an event

Resolve → validate → authorize → commit → acknowledge → fan-out. Persist the event and routing intent together. An OK confirms local durability; remote delivery proceeds independently. The event never crosses another tenant’s runtime implicitly.

Own the domain, reuse the wire protocol.

Use a Khatru adapter for Nostr transport and hooks. Tinyrelay owns admission, transaction boundaries, lifecycle, routing and telemetry. The web surface uses Go HTML templates and ordinary form handlers. Start with one Khatru instance per active tenant; do not mutate framework hooks during concurrent requests.

Every task belongs to a context, has a stop path, and is joined on shutdown. The registry never holds a global lock during SQL or network I/O. Live subscriptions remain in memory and are rebuilt by reconnecting clients after restart.

Concurrency without a second platform.

Readers run concurrently; each tenant serializes short writes. A shared scheduler fairly dispatches due jobs, backed by persistent tenant state. Each socket has a single writer and bounded pending output; a slow consumer is disconnected with a reason.

Runtime eviction requires zero connections, zero in-flight requests and no running task. Due jobs reacquire the tenant. Closing an idle database releases handles; it never deletes relay state.

03

Create owned relays on demand.

Provisioning is a durable control operation. Activation is a transient runtime concern. Neither introduces a lease.

Durable identity

An authorized operator creates a relay with a stable internal ID, unique name, owner pubkey and template revision. A configured owner allowlist may self-provision through signed management requests. There is no open anonymous creation door by default.

creating→ready↔disabled

Deletion is explicit. Disabling closes access and pauses delivery while preserving data. No idle timeout, owner inactivity or calendar date deletes a relay. Content expiry under NIP-40 is separate.

Runtime lifecycle

Resolve a registered host or path, acquire its runtime, and lazily open the tenant database. Single-flight activation prevents two runtimes from owning the same tenant. Unknown names return an error and allocate nothing.

unloaded↔active→draining

A database handle cache is a host implementation detail, not a relay-count limit. Background jobs can activate a relay even with no connected clients.

Creation spans catalog and tenant files: write an idempotent “creating” catalog record, initialize the tenant database and owner, then mark ready. Only ready records are routable. Startup completes or reports interrupted creation. Unique names, idempotency keys and a data-directory process lock prevent duplicate ownership.

Keep configuration portable; make behavior explicit.

A personal bundle creates three ordinary named relays: alice-outbox, alice-inbox and alice-dm. Each has its own database and policy. A bundle is an additional provisioning convenience. Preserve the full existing template catalog: default, outbox, inbox, private, chat, media, search, articles, dm, quiet, site, marmot, grasp, marmot-members and home, together with their connection templates and source-dependent jobs.

Compile once

Validate JSONC against a strict schema. Resolve an immutable revision into a typed policy snapshot. No JavaScript, WASM, shell interpolation or arbitrary code execution inside templates.

Change deliberately

Plan/apply/export remain first-class. On update, omitted sections stay unchanged; an empty list explicitly clears a list. Reject unknown fields and use a revision precondition to prevent lost updates.

Publish capabilities truthfully

Template files do not hot-change existing tenants. Applying a revision records an audit entry and swaps the policy atomically. Generate NIP-11 from a build capability registry intersected with tenant-enabled features; only conformance-tested capabilities enter that registry.

Preserved semantics: bindws config.ts, relay template contract, connection shortcuts. App shortcuts stay presentation metadata; visibility never substitutes for authorization.

NIP-65 defines public relay-list discovery, not a server delivery guarantee. NIP-17 uses kind 10050 for DM relays and recipient-restricted gift-wrap reads. These are distinct from a public mentions inbox.

Automatic begins after explicit setup. Creating a personal bundle enables its local policies and workers. The console prepares merged kind-10002 and kind-10050 updates for the owner’s NIP-07/NIP-46 signer. The daemon never possesses the owner’s secret key or pretends its relay key is that owner. Display “discovery not published” until the signed lists are published.
Record intent

In the event transaction, add durable routing intent with origin and policy revision. A cold discovery cache never blocks a local publish on network I/O.

Resolve destinations

Read the newest verified signed lists; use configured indexers on cache misses. Persist each normalized destination independently. Missing lists remain visible as unresolved work.

Attempt delivery

Reuse connections by endpoint and authentication context. Correlate each OK with its event ID. Record attempts, next-attempt time and structured outcome per target.

Recover & report

Retry transient failures with jittered backoff. Duplicate remote acceptance is success. Permanent rejections remain inspectable and can be retried deliberately.

The delivery contract

  • At-least-once attempts, with idempotency by tenant + event ID + destination. A crash after remote acceptance can cause a duplicate retry.
  • Local OK ≠ remote delivery. Accepted means committed locally with routing intent when enabled. The console reports remote status separately.
  • No silent queue eviction. Pending intent stays on disk through temporary outages. Optional expiry is an explicit operator retention policy, never a hidden tenant ceiling; expiry, deletion or cancellation records a terminal status.
  • Policy is checked again before sending. A deletion, expiration, disabled relay, revoked author or newly private policy cancels now-ineligible work.

Discovery and network boundaries

  • Verify IDs and signatures on list events; resolve replaceable-event ordering deterministically. A list refresh changes future routes and revalidates pending destinations. Send the author’s verified kind-10002 list alongside public distribution as NIP-65 recommends.
  • Track inbox progress per source and filter; NIP-01 time-window pulls cannot prove a complete history. Surface partial backfills; late/backdated events require reconciliation.
  • Block loopback, link-local, metadata and private-network egress by default, including resolved IPs on every dial. Operators may explicitly allow LAN relays. Normalize aliases to prevent self-delivery loops.
  • If an upstream requires owner AUTH, report an authentication requirement and use a scoped external signer only when explicitly configured. A relay’s service key is a different identity and cannot impersonate its owner.
Job ownership and inbox checkpoint rules

Unique delivery keys prevent duplicate queue rows. Workers claim due rows using an atomic conditional update that records a reservation token and expiry; long tasks renew ownership. Completion updates must match the token, fencing stale workers from overwriting newer state. Cancel expired work before reclaiming it locally. Remote relays do not support this fencing token, so remote duplicate sends remain possible and are part of the at-least-once contract.

One job owns each tenant/source/filter checkpoint. Commit ingested event batches and their replay checkpoint together where the source exposes a usable cursor. For time-window Nostr queries, advance the completed window only after all returned events are committed and EOSE is received; otherwise replay that window with overlap and ID deduplication. Never derive a completed checkpoint from the greatest timestamp seen so far.

Remote availability and client discovery cannot be guaranteed. Local workers can use already verified lists or configured targets immediately after setup; new endpoints become discoverable to other clients only after the owner signs and publishes updated lists. Public inbox collection is limited to selected sources. Following an owner’s contact list to build a feed is a separate optional mirror job.

Prior behavior: HAVEN combines role-specific relays, inbox gathering and outbox broadcasting. Bindws already implements NIP-65 delivery and per-target push cursors; its NIP-9a callbacks are a distinct delivery service required for parity, with their own registration, authorization, retry and revocation behavior.

Durability is part of the fast path.

Start with SQLite because events, policy changes and delivery intent can share one transaction. Choose a different engine only when measured costs justify a new consistency model.

Use stable generated IDs for directories; relay names are catalog aliases. Event IDs deduplicate within a tenant, never globally across private tenants.

One transaction, one truthful acknowledgement.

Validate the event’s canonical ID and signature, apply authorization and content rules, then begin a short write transaction. Recheck the policy revision. Atomically apply replacement/deletion semantics, indexes and required delivery intent; commit before sending a successful stored-event OK.

Use WAL, one write connection per tenant, short read transactions and a small read pool. Set durability pragmas explicitly on every applicable connection. Start with synchronous=FULL; make a weaker durability mode an explicit later choice, never a silent throughput tweak.

SQLite WAL supports concurrent readers with one writer per database. Long readers can delay checkpoints. A local filesystem is required for this layout; a shared NFS volume is not a multi-node scaling mechanism.

SQLite WAL | synchronous durability

Correctness invariants to test before optimization
  • Every ingest source uses the same validation/storage service; internal imports carry an explicit authority and origin, not a blanket policy bypass.
  • Replaceable and addressable events obey timestamp and ID tie-breaking. Authorized deletion, deletion-before-arrival tombstones, expiry and index cleanup are transactional.
  • Ephemeral events are never persisted and have a distinct acceptance contract. Duplicates do not create extra routing intent.
  • Reads, COUNT, search, sync and live fan-out enforce the same visibility policy; private data cannot leak through counts or auxiliary paths.
  • Register a subscription against a commit sequence barrier; read its bounded snapshot, then drain buffered later commits. Deduplicate overlaps and send EOSE after the historical snapshot.
  • Policy tightening invalidates affected subscriptions. Slow readers cannot pin a SQL cursor while waiting on a network socket; page or materialize bounded batches.
  • Crash before commit yields no successful OK; crash after commit preserves the event and intent. Local live delivery is best effort; reconnect queries recover durable events.
  • Disk-full or I/O failure rejects the write before OK. Stop accepting affected writes and report storage health; never report durable success from an in-memory queue.
Query strategy and the storage-adapter decision

Begin with indexes for ID, author/time, kind/time, author/kind/time and tag name/value/time. Order by creation time and ID, limit each filter as the protocol requires, deduplicate unions, and use keyset iteration for jobs. Record query plans and rows visited in developer benchmarks. Add FTS only with the search milestone.

The proposed SQLite store must own atomic event + intent writes. Khatru’s storage hooks can delegate to that service; do not enqueue from an after-save callback. Eventstore is useful as an adapter/reference, but its event-only interface does not establish a transaction spanning a separate job database. A split event engine would require a durable change journal and recovery protocol.

The first implementation spike must prove atomic replacement/deletion, truthful query errors, the historical/live handoff, per-event private visibility and runtime shutdown through Khatru. If hooks cannot preserve these invariants, keep the SDK and implement the small missing protocol/lifecycle adapter directly.

Backup, restore and tenant isolation

Use SQLite’s online backup API or a coordinated quiescent snapshot, never copy a live main database file alone. A manifest records schema, tenant IDs, config revisions, event counts, checksums and key references. Encrypt backups containing signing keys. Optional blob storage needs a manifest-consistent snapshot with garbage collection paused for the backup.

Restore into a new directory, validate hashes/schema, run integrity and protocol checks, and default restored outbound workers to paused so a rehearsal cannot rebroadcast. Catalog/tenant backups reconcile by stable ID. Logical isolation is enforced in code and files; one process is not a security sandbox against malicious extensions or host compromise.

SQLite backup API. Proposed reliability target: preserve every successfully acknowledged stored event across process restart and, with FULL sync and a correctly functioning storage stack, power loss; a single host is still a hardware failure domain.

Useful telemetry with bounded cardinality.

Labels come from a fixed vocabulary: operation, transport, event class and outcome. No event IDs, pubkeys, tenant names, subscription IDs, arbitrary kinds, URLs or full filter text in metric labels. Hashing those values does not reduce cardinality.

Provide authenticated, on-demand tenant diagnostics for detailed state. Exclude event bodies, ciphertext, keys, tokens, full URLs and identifiers from default traces/logs. Management audit records have a separate access and retention policy.

Prometheus naming and label guidance

Sampling and overhead are design choices.

Start with low-rate head sampling for traces. Record errors as counters/logs regardless of trace sampling; head sampling cannot promise to retain every slow/error trace. An optional collector with tail sampling can retain those traces when configured to receive them.

Exporter failure never blocks acceptance. Bound export queues, count dropped telemetry, and compare instrumentation on/off in the benchmark harness. Use low-rate diagnostic sampling and opt-in mutex/block profiling.

OTel sampling | histogram guidance

First operational view: traffic and outcomes; accept/query latency; fan-out pressure; delivery age and retries; SQLite/WAL/checkpoints; CPU, RSS and goroutines. Alert on sustained inability to make progress, disk headroom and recovery failure. Keep tenant debugging in the admin view.

Reproducible load, not a marketing score.

Acceptance gates before capacity targets.

Release gates: no cross-tenant/private visibility leak; no loss of acknowledged stored events in restart tests; no orphaned routing intent; duplicate retries converge; backlog drains when a healthy target recovers; RSS/goroutines stabilize after churn.

Choose numeric service objectives after the first representative baseline on the intended host. Gate a performance change on repeatable improvement in its target metric and no material regression in p99, memory, errors or durability. Run race tests separately from timing benchmarks.

09

A service an operator can understand.

The executable is tiny: run the daemon with tiny serve and use the same command for management. Ship plain HTML management pages, a systemd example and an optional container image. The default deployment is one host and one data directory.

Preserve UX through simpler presentation. Every retained bindws task must be achievable from the web interface with equivalent authorization, inputs, preview, progress, outcome and recovery. Rebuild with basic HTML and forms; no bindws branding, CSS or generated console bundle carries over. Simplifying markup does not permit removing a workflow or forcing an existing web task into the CLI. This document’s presentation is not the product design.

All workflows, ordinary pages

Keep the full People, Moderation, Rules, Identity, Connect, Data, Sync, Views, Health and Owner workflow families. Include files, sites, Git, invitations, list recovery, ownership/succession and callback management. Navigation may become links and forms rather than tabs; role-specific actions remain discoverable.

Preserve public event/article pages, feeds, cards, QR handoff, connection shortcuts and sign-in. Use GET for reads and POST for mutations, followed by clear results. Render plan/preview and validation on the server. Long-running work keeps progress and retry/cancel actions; small scripts or polling can preserve time-sensitive feedback where plain refresh would worsen the task.

Keep extension and remote signing

Rebuild the NIP-07/NIP-46 helper so existing extension, phone pairing and remote-signer flows remain supported, including their relay transport and discovery behavior. Never ask users to paste a private key. Any browser session bridge uses an origin-bound, expiring one-time challenge, Secure/HttpOnly/SameSite cookies, CSRF protection and per-action authorization.

Preserve the signed NIP-98/NIP-86 contracts for scripts and clients, with documented exceptions for removed fuel/lease operations. Keep signer scripts isolated from page rendering. The CLI is an additional complete interface; it is not a substitute for missing web functionality.

Serving and access

  • TLS proxy fronts a loopback-bound HTTP/WS listener. Use explicit hosts or wildcard DNS/certificates, or a single domain with relay paths.
  • Trust forwarding headers only from configured proxies. Match canonical host/path against the registry; validate custom-domain ownership before alias activation.
  • Host admin uses a local socket or separately authenticated control endpoint. Relay owners manage only their tenant via signed NIP-98/NIP-86 operations.
  • Diagnostics are private. Tenant signing keys are distinct from owner keys and stored outside exported template files.

Restarts, backups and capacity

  • On shutdown, stop admission, drain accepted writes, cancel/join workers, close sockets and release databases. Clients reconnect and reissue subscriptions.
  • On startup, check schema versions, reconcile incomplete creation and recover expired task reservations. Persist due times; the scheduler’s heap is only a cache.
  • Expose liveness separately from readiness and per-tenant storage health. A remote relay outage does not make local ingest unready.
  • A single host does not provide automatic failover. Scale vertically first; multi-host placement is a separate topology choice after application parity. Never run two owners over the same tenant files.
Task reservations are internal crash-recovery state. They are short worker ownership records, unrelated to relay lifetime. User relays remain owned and persistent; there is no leased-relay feature anywhere in the runtime model.

Move every service to a local implementation.

Blossom/NIP-96 use local content-addressed files, streaming uploads and atomic publication. Sites retain manifest verification, mirroring, authenticated access and isolated origins. GRASP retains its signed authorization and event/object publication boundary while its storage adapter may use native Git. Marmot, views, succession, owner notifications and callbacks run through durable local jobs. All are required implementation work, even where a tenant can disable them.

11

Decisions this plan makes.

These defaults are concrete enough to implement. A few choices remain experiments, with evidence required to change direction.

D01 / Adopt

Single daemon, logical tenant isolation.

Reduces deployment and coordination cost. Tradeoff: a process or host failure affects every resident relay. Strong process isolation or multiple hosts is a later deployment choice.

D02 / Adopt

No fuel, trials or relay leases.

Owner is assigned at creation; lifetime is indefinite. Remove economic and lease concepts entirely. Keep operator flow control separate from tenant content rules.

D03 / Start here

SQLite per tenant, FULL sync.

Enables event + intent atomicity and simple tenant backup/movement. Tradeoff: one writer per tenant, file-handle management and fsync cost. Compare modernc/cgo only under the same durability contract.

D04 / Prove in P0

Khatru adapter + current Nostr toolkit.

Reuse protocol work while preserving ownership of the domain. Keep the adapter contingent on lifecycle, transaction and visibility tests; do not inherit framework limits without inspection.

D05 / Adopt

Declarative templates with immutable revisions.

A template changes policy and services; it never runs tenant code. A personal bundle is a family of standard relay instances, each independently manageable.

D06 / Adopt

Local acceptance; asynchronous distribution.

Durable routing intent is committed with the event. Delivery is at least once and independently observable. Private DM routing remains separate from public fan-out.

D07 / Adopt

Metrics now; optimization when measured.

Ship a stable low-cardinality metric vocabulary, logs and optional tracing with the first slice. Numeric capacity targets follow baseline measurements on the intended host.

D08 / Required

Full functional and UX parity.

All retained bindws features, APIs, templates, data and user journeys are required. Blobs, sites, Git, Marmot, views, callbacks and succession are part of completion. Phases sequence this work; a subset does not satisfy the project.

D09 / Adopt

Plain HTML with complete workflows.

Carry over no bindws branding or styling. Preserve tasks, permissions, input/output behavior, signing, previews, progress, sharing and recovery through simple pages/forms and focused helpers. Keep all existing web tasks available on the web.

D10 / Separate concern

Local application parity; optional clustering.

Replace Worker mechanisms with local services and finish the complete application on one host. Multi-host placement or automatic failover can be separate deployment work; neither is a reason to omit application capabilities.
